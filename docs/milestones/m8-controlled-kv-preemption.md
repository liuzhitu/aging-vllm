# 里程碑：M8 受控 KV 准入抢占

状态：代码已修改，待统一 GPU 验证；尚未验收。日期：2026-10-12。

最新修订：按用户要求增加无进展恢复、完整输入准入、抢占后停止新接纳和重算成本排序；下文反映当前实现。

## 目标

动态优先级靠前的请求因 KV Cache（注意力键值缓存）不足无法执行时，在等待达到阈值、存在较低优先级持有者、且释放后确实能执行的条件下进行抢占。覆盖首次 prefill（输入预填充）、续算 prefill 与 decode（逐 token 解码）的按需容量检查。

## 调查

本轮在 M7a/M7b 未提交改动上继续实现，保留现有学习文件与记录。HEAD 为 `bde300ea63a8f24a92db3b1135ef605cae04a729`。M7 的 GPU 验收尚未完成。

M7b 的 aging（按未获服务时间排序）路径只跳过被 KV 阻挡的 prefill；decode 遇到扩容失败会逐个释放排序靠后的运行请求，没有先判断释放是否足够，也没有等待阈值。waiting 队列中的部分 prefill 同样持有 KV，原抢占分支未考虑它们。

执行路径仍为 `LLMEngine.step()` → `Scheduler.schedule()` → `_schedule_aging()` → `BlockManager` 容量接口 → `ModelRunner.run()` → `postprocess()`。

## 设计

仅当本轮 token 预算和请求名额仍足够、实际 KV 容量检查失败时考虑抢占。默认等待阈值 50 ms，以 `now - last_service_time` 计算；每轮 now 只读取一次，不把扫描耗时变成不同候选的阈值差异。

候选 victim（受害者）来自当前候选列表中排序更靠后的请求，要求持有 KV、本轮未被抢占。这个范围天然排除当前请求、较高优先级请求以及已经入选计划的请求。允许集合内部按有效 KV token 数从少到多选择，成本相同再按最近获服务者优先。

累计 victim 后模拟其引用释放；找到第一个足够准入的前缀集合才真实释放。如果所有允许 victim 都不足，不改变任何队列或 KV 所有权。一轮最多成功完成一次主动抢占决策，可以包含多个 victim。被抢占请求本轮不再入选；此后也不接纳后续尚未持有 KV 的请求。

正常扫描完全没有选中请求时，进行一次强制抢占扫描，绕过等待阈值，仍要求 victim 优先级更低且释放预检查有效。第一次扫描没有计划意味着没有真实分配或成功抢占，所以重试不会重复执行已经提交的动作。第二次仍为空才沿用明确的无进展错误。

## 实现

### `nanovllm/config.py`

新增 `preemption_wait_ms: float = 50.0`，要求有限且非负，0 表示 KV 阻塞时无需额外等待。默认值是实验起点，不代表性能最优配置。scheduler 转为秒与单调时钟比较。decode_first 对照路径不使用该阈值。

新增 `scheduler_reserve_full_isl: bool = True`。aging 路径中，首次接纳和抢占后的恢复以当前全部 token 序列为容量检查终点；实际 `allocate()` 仍以本轮计算终点为参数。恢复请求的完整序列包含 prompt 和历史输出。此开关是准入检查，不是预分配全部空间，也不是为未来未知输出作永久容量承诺。

### `nanovllm/engine/block_manager.py`

新增 `can_schedule_after_preempt(seq, num_tokens, victims)`，不修改真实状态。

通过 `Counter`（引用次数计数）累计 victim 对每个块的持有次数。模拟空闲容量是当前空闲块数加上所有引用将被释放的块数。共享块只能计一次，不会把多个 block_table 长度直接相加。

已有 block_table 的候选，需求是本轮目标块数减去已有块数。首次分配的候选，目标容量扣除模拟释放后仍有持有者的缓存前缀；失去最后一个持有者的缓存块虽然进入空闲池，采用它仍消耗一个空闲块，因此不能同时把它算作免费共享。

已有 `can_allocate()`、`can_append()`、实际分配、引用计数及哈希登记不改。模拟基于同一按需终点及缓存采用语义；结果与实际分配的一致性仍需 GPU 验证。

### `nanovllm/engine/scheduler.py`

- `_schedule_aging()` 统一首次分配与扩容的可执行判断；首次分配按配置检查完整序列，现有持有者仍只检查本轮扩容；失败后检查等待阈值及本轮抢占次数。
- 正常扫描为空时，最多额外调用一次 `_schedule_aging(force_preemption=True)`，解除阈值导致的无进展阻塞；不是无限递归，不放宽优先级或容量约束。
- `_preempt_for_kv()` 从较低优先级持有者中按 `(num_cached_tokens, -last_service_time, -seq_id)` 排序，然后累计并调用只读容量预检查。有效 KV token 数是重新构建工作量的保守代理；没有新增成本缓存或声称预测 GPU 毫秒耗时。
- 预检查成功后，按请求当前状态从 running 或 waiting 中移除，再复用 `preempt()` 释放并重新加入 waiting。保留 token 历史及服务时间，KV 计算进度被重置。
- 本轮 `preempted` 集合过滤旧阶段快照，避免重复入选；`preemption_used` 标记只在真实抢占成功后设置，失败预检查不消耗本轮决策机会。
- 发生抢占后，后续没有 block_table 的新请求和恢复请求不再接纳；当前通过抢占获得空间的赢家继续完成分配。已有 KV 的部分 prefill 虽在本地 waiting 中，仍可以续算。这按资源驻留区分，不能机械地停止整个 waiting 集合。
- 移除 aging 原来的先释放 decode victim 和自身回退逻辑，避免绕过阈值与释放前检查。decode_first 分支保持原逻辑。
- `postprocess()` 不变，真实计算成功才提交进度和更新时间。

运行流程：

```text
动态排序 → 本轮计算量 → KV 容量不足
  → 等待达到阈值、尚未使用本轮抢占机会
  → 选择较低优先级持有者、模拟释放
  → 足够则移出原队列并抢占
  → 分配候选本轮 KV → 执行 → 成功提交
```

## 工程记录

### 架构决策

容量预测放在 BlockManager，队列优先级与阈值放在 Scheduler。只读预测与真实释放严格分开，复用现有实际 KV 所有权管理，不新增持久抢占计数、冷却时间或动态分数。

### 不变量

- 容量模拟不修改引用计数、空闲池、哈希、队列或请求进度。
- 预检查无可行集合时零释放；真实释放只取既定 victim 顺序中第一个足够的前缀。
- 受害者必须优先级更低；已入选请求不能被抢占。
- 请求先从原队列移除再重新入队，每个被抢占请求本轮只处理一次。
- 一轮最多成功执行一次主动抢占决策，重入队不重置服务时间。

### 缺陷或新发现

当前 scheduler 不支持返回空计划并等待。无进展时已新增一次绕过阈值的恢复扫描；如果释放较低优先级持有者也无法满足准入，仍报 RuntimeError，而不是休眠或无限重试。例如完整序列超过整个池的容量，或者允许集合无法提供足够空间。这是当前支持边界，不宣称已解决所有内存拥塞。

单轮一次抢占与等待阈值不能完全避免跨轮反复重算；恢复 prefill 的成功计算也会更新时间。容量预检查反复累计候选可能增加控制面耗时，均待 GPU 负载实验观察。

完整输入准入和抢占后停止接纳降低过度接纳风险，但没有为所有活跃请求永久预留未来扩容空间，因此不是绝对防抖保证。成本排序以逐请求有效 token 数作启发式：忽略缓存实际存活、上下文位置和内核耗时；按这个顺序找到的最短可行前缀也不一定是全局最低总重算成本组合。后续需记录实测重算 token 数和请求进度，不提前声称最优。
